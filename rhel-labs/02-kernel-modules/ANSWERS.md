# 02 — модули ядра: ответы на вопросы

Ответы опираются на выводы из README (стенд `rhel10-lab`, RHEL 10.2) и на
официальные источники: документация RHEL 10 «Managing, monitoring, and updating the
kernel», глава 3; `man modprobe`, `man modprobe.d`, `man modules-load.d`.

## Часть 1

**Что показывает третья колонка `lsmod` и почему по ней видно, можно ли выгрузить модуль?**
Счётчик использования и список модулей, которые от этого модуля зависят. Пока
счётчик не ноль, ядро модуль не отдаст: у `xfs` на стенде там `1` — корневая
файловая система, у `udp_tunnel` после `modprobe vxlan` — `1 vxlan`.

**Почему в `/lib/modules/` на стенде два каталога?**
Установлено два ядра (модуль 01), у каждого свой набор модулей. Модуль собран под
конкретное ядро — это видно в поле `vermagic` вывода `modinfo`.

**Какой командой узнать параметры модуля, не загружая его?**
`modinfo -p <модуль>`; в полном выводе `modinfo` это строки `parm:`.

## Часть 2

**Чем `modprobe -r vxlan` отличается от `rmmod vxlan` по результату?**
`modprobe -r` выгружает модуль и зависимости, которые после этого никому не нужны:
на стенде исчезли все три модуля. `rmmod` выгружает только названный: `udp_tunnel` и
`ip6_udp_tunnel` остались со счётчиком 0.

**`modprobe dummy numdummies=3`, ошибок нет, а интерфейсов по-прежнему два. Почему?**
Модуль уже был загружен. Параметры читаются один раз, при загрузке; повторный
`modprobe` загруженного модуля ничего не делает и завершается с кодом 0. Нужно
`modprobe -r dummy`, затем `modprobe dummy numdummies=3`.

**Где искать причину, если `insmod` ответил «Unknown symbol in module»?**
В `dmesg`: ядро перечисляет, каких функций не хватило. На стенде это были функции из
`udp_tunnel` — зависимости, которую `insmod` не загрузил.

## Часть 3

**Какая служба читает `/etc/modules-load.d` и как проверить файл без перезагрузки?**
`systemd-modules-load.service`. Проверка: `systemctl restart
systemd-modules-load.service`, затем `lsmod` и журнал службы — там строка
`Inserted module`.

**Параметр записан в файле, но не действует. Какие две команды покажут причину?**
`modprobe -c | grep -E '^options dummy'` — все строки options из всех файлов, и
`modprobe --show-depends dummy` — команда, которую `modprobe` выполнит. На стенде обе
показали `numdummies=2 numdummies=0`.

**Почему переименование файла в `zz-lab-dummy.conf` исправило дело?**
Строки options из всех файлов складываются в порядке имён файлов, и при повторе
параметра действует последнее значение. `lab-dummy.conf` шёл раньше `systemd.conf` с
его `numdummies=0`, `zz-lab-dummy.conf` идёт позже.

**Чем настройка в `/run/modprobe.d` отличается от настройки в `/etc/modprobe.d`?**
`/run` живёт в памяти: после перезагрузки файла нет — на стенде `ls -l
/run/modprobe.d/` показал `total 0`, и интерфейсы `dummy` не появились. Настройка в
`/etc` постоянная. Файл в `/etc` перекрывает одноимённый файл в `/run`.

**Загрузка стала занимать пять минут. Какими командами найти виновника?**
`systemd-analyze` — сколько заняла загрузка, `systemd-analyze blame` — какие службы
дольше всех, затем `journalctl -b -u <служба>`. На стенде это была
`cloud-init-local.service` (4 мин 23 с): она пыталась получить адрес через `dummy0`.

## Часть 4

**Что запрещает строка `blacklist dummy` и чего она не запрещает?**
По `man modprobe.d` она велит игнорировать внутренние псевдонимы модуля, то есть не
загружать его автоматически. На стенде её учитывает служба автозагрузки (`Module
'dummy' is deny-listed (by kmod)`) и `modprobe -b`. Явный `modprobe dummy` модуль
всё равно загружает; не мешает она и загрузке модуля как зависимости другого.

**Зачем в документации к ней добавлена строка `install dummy /bin/false`?**
Чтобы отказ получала любая загрузка через `modprobe`, включая явную и загрузку по
зависимости. `modprobe` вместо модуля выполняет `/bin/false` и завершается ошибкой.

**Как узнать, нужно ли пересобирать initramfs после запрета модуля?**
`lsinitrd /boot/initramfs-$(uname -r).img | grep <модуль>`. Если модуль там есть, он
загрузится до чтения `/etc/modprobe.d`, и нужен `dracut -f -v`. `dummy` на стенде в
initramfs нет.

**Чем запрет параметром `modprobe.blacklist=` в меню GRUB отличается от файла в `/etc/modprobe.d`?**
Параметр, дописанный в меню GRUB, действует одну загрузку (раздел 3.8
документации). Файл в `/etc/modprobe.d` действует постоянно.

## Итоговые вопросы

**1. Чем загруженный модуль отличается от установленного?**
Установленный — файл в `/lib/modules/<версия ядра>/` (на стенде их 2255, смотреть
`find`, `modinfo -n`). Загруженный — часть работающего ядра (на стенде 44, смотреть
`lsmod` или `/proc/modules`).

**2. Почему для загрузки предпочитают `modprobe`, а не `insmod`?**
`modprobe` находит модуль по имени, загружает зависимости по `modules.dep` и
применяет настройки из `modprobe.d`. `insmod` требует путь к файлу, зависимостей не
знает и настроек не читает.

**3. Где задаётся автозагрузка модуля, а где его постоянные параметры?**
Автозагрузка — имя модуля в `/etc/modules-load.d/*.conf`. Параметры — строка
`options` в `/etc/modprobe.d/*.conf`. На стенде так настроен `brd`: после
перезагрузки `/sys/module/brd/parameters/rd_nr` равен 2.

**4. Два файла задают один параметр по-разному. Какое значение подействует?**
Последнее в порядке имён файлов. Проверка без загрузки модуля — `modprobe
--show-depends <модуль>`: параметры перечислены в том порядке, в каком будут
переданы.

**5. Чем `blacklist` отличается от `install <модуль> /bin/false`?**
`blacklist` отключает автоматическую загрузку, но не явную команду. `install ...
/bin/false` подменяет загрузку командой, которая всегда завершается отказом.

**6. В каком случае запрет модуля требует пересборки initramfs?**
Когда модуль входит в initramfs. Тогда по документации (раздел 3.10) делают копию
образа и выполняют `dracut -f -v`.
